# Инструкции по работе с проектом

## Продукт и статус

Проект — сервис обмена бумажных книг за баллы с доставкой. Подписочный прокат — будущий этап. Сейчас в репозитории документация и проект REST API; работающий backend и клиентские приложения ещё не реализованы.

Подтверждённые правила:
- Баллы начисляются только после окончательной приёмки оператором, а не после передачи курьеру или в постамат.
- Полученная за баллы книга остаётся в собственности пользователя.

Остальные проектные допущения и открытые вопросы описаны в `docs/api-design.md`. Не представляй их как подтверждённые решения. Старые схемы user flow и `docs/idea.md` могут содержать первоначальный момент начисления баллов; при работе с ними учитывай уточнения выше.

## Выбранный стек

- Backend: Python, FastAPI, SQLAlchemy.
- Данные и инфраструктура: PostgreSQL, Redis, MinIO, Caddy.
- Mobile: Flutter.
- Web: React, TypeScript.

Следуй выбранному стеку. Дополнительные библиотеки выбирай по конкретной потребности и объясняй существенные изменения архитектуры. Версии и команды запуска приложений фиксируй после появления реальной конфигурации проекта.

## Архитектурные правила

- Развивай backend как модульный монолит с общим REST API для мобильного приложения, сайта и операторской панели.
- Держи бизнес-правила в сервисах модулей; HTTP-обработчики отвечают за входные данные, авторизацию и вызов сервисов.
- Разделяй описание издания (`Book`) и физический экземпляр (`Copy`).
- PostgreSQL — источник истины для заказов, экземпляров и баллов. Redis — для временных данных и конкретных инфраструктурных задач.
- Веди неизменяемый журнал операций с баллами. Начисление, списание и возврат выполняй атомарно с соответствующими изменениями заказа или приёмки.
- Защищай операции от повторных запросов и конкурентного заказа одного экземпляра. Проверяй допустимость переходов статусов на сервере.
- Выполняй внешние действия через фоновые задачи с повторными попытками; сохраняй бизнес-изменение и outbox в одной транзакции.
- Храни фотографии в закрытом MinIO bucket; проверяй владельца, формат и размер, выдавай временные ссылки.
- Проверяй роли и владение ресурсами на backend. Не записывай секреты и токены в код, документацию или логи.

## Документация и API

- `docs/idea.md` — исходная идея.
- `docs/api-design.md` — правила API, подтверждённые уточнения и допущения.
- `docs/yandex-id.md` — проект интеграции Яндекс ID и её текущие ограничения.
- `docs/build_openapi.py` — текущий источник генерации контракта.
- `docs/openapi.json` и `docs/swagger.html` — генерируемые результаты.
- `docs/user-flow.md` и `docs/user-flow.png` — пользовательские сценарии.

При изменении API редактируй генератор и связанные правила, затем перегенерируй JSON и Swagger UI. Не правь генерируемые файлы отдельно от источника. При появлении FastAPI-приложения сохраняй соответствие реализации и контракта; смену источника генерации документируй.

Для Яндекс ID различай OAuth-токен провайдера и собственные токены сервиса. Проверяй Яндекс `client_id` по серверному allowlist и связывай пользователя по `(provider, provider_user_id)`. Полный браузерный вход пока не описан контрактом; перед его реализацией дополни документацию.

## Проверки и рабочий процесс

- Перед изменениями прочитай относящиеся к задаче документы и код. Учитывай более конкретные инструкции вложенных `AGENTS.md`, если они появятся.
- Для обновления API-документации из корня проекта выполни `python docs/build_openapi.py`. Генератор проверяет ссылки, operationId и параметры путей; это не полная валидация OpenAPI и не тест backend.
- Для изменений бизнес-логики проверяй значимые сценарии: повтор операции, недостаток баллов, конкурентное резервирование, отмену и доступ к чужим ресурсам.
- Используй команды проверок из фактической конфигурации проекта. Не сообщай об успешных тестах, которые не запускались.
- Держи изменения в рамках задачи, сохраняй работу пользователя и обновляй затронутую документацию.
- В итоговом сообщении кратко укажи изменения, выполненные проверки и оставшиеся ограничения. Общайся с пользователем на русском.
