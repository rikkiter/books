# Интеграция Яндекс ID

Проверено по официальной документации 2026-10-04. Это проект интеграции: реальный вход с зарегистрированным OAuth-приложением пока не проверялся.

## Flutter: контракт текущей версии

1. Зарегистрировать приложение в Яндекс OAuth, настроить iOS/Android по инструкциям соответствующего LoginSDK. Client ID — публичная настройка. Client secret в мобильный бинарник не помещать.
2. Подключить официальный нативный LoginSDK через проверенную Flutter-обёртку или собственный platform channel. Выбрать получение **OAuth-токена**. LoginSDK также умеет выдавать JWT, но текущий API этот вариант не поддерживает.
3. После успешного входа отправить `POST /api/v1/auth/yandex` с JSON `{"access_token":"<yandex_oauth_token>"}` по HTTPS. Не передавать user ID, роль, client secret или email как доказательство входа.
4. Backend отправляет `GET https://login.yandex.ru/info?format=json`, заголовок `Authorization: OAuth <token>`. Токен не помещать в URL. Обязательны таймаут, проверка TLS и обработка ошибок провайдера.
5. Проверить непустой строковый `id` и совпадение `client_id` с allowlist зарегистрированных приложений сервиса. Список хранится на сервере; client_id из тела запроса не является доверенным. Для отдельных OAuth-приложений web/iOS/Android разрешить только их реальные ID.
6. Найти или создать связь с уникальным ключом `(provider='yandex', provider_user_id=id)`. Хранить ID как строку. Не использовать email/login для автоматического объединения аккаунтов. `psuid` зависит от OAuth client_id, поэтому для общего аккаунта между платформами используем `id`.
7. Выдать **собственные** access/refresh tokens. Роль при создании — user; оператора назначает администратор вне входа. Ответ не кешировать. Провайдерский токен после проверки не сохранять; исключить его и собственные токены из access/error/APM-логов.
8. Flutter хранит собственный refresh token в защищённом хранилище. `/auth/refresh` обновляет нашу сессию, не токен Яндекса. `/auth/logout` отзывает нашу сессию, не разрешение приложения в Яндексе.

Именованные ошибки: `INVALID_PROVIDER_TOKEN` и `PROVIDER_CLIENT_MISMATCH` — 400, `IDENTITY_PROVIDER_UNAVAILABLE` — 503. Отмена пользователем в SDK не создаёт запрос к backend. Недоступность Яндекса нельзя трактовать как успешную авторизацию.

## Права и профиль

Запрашивать только нужные права из настроек OAuth-приложения. Для отображаемого имени можно использовать право на базовые сведения; email, фото, телефон, дата рождения не нужны как обязательные условия входа в MVP. Если нужного имени нет, использовать login или предложить заполнить профиль. Состав ответа зависит от разрешённых прав: нельзя считать email/phone обязательными.

Документация Яндекса допускает запрос `/info` и с токенами других сервисов. Поэтому успешный ответ `/info` сам по себе недостаточен для нашего сервиса: проверка client_id — обязательное правило нашего backend.

## React: пока не полный контракт

Текущий `/auth/yandex` описывает обмен уже полученного OAuth-токена. Он не задаёт полный браузерный вход, callback и cookie-сессию. Формулировка старого черновика «через SDK/OAuth» скрывала этот пробел.

Предлагаемый веб-сценарий для следующей версии: backend начинает Authorization Code flow, сохраняет одноразовую транзакцию входа, генерирует state и PKCE S256; после callback проверяет state и привязку к браузеру, обменивает code на `/token`, проверяет `/info`, устанавливает собственную HttpOnly/Secure cookie и переводит пользователя на разрешённую страницу. Client secret хранится только на backend. Redirect URI фиксируется в настройках Яндекс OAuth; произвольный URL от клиента не разрешён. Callback не содержит собственных токенов в URL. Мутации с cookie требуют CSRF-защиты.

Это проектное предложение, а не реализованные endpoints. Для его добавления нужно определить домены web/API, same-site/cross-site размещение и стратегию cookie. Не смешивать его с отправкой SDK JWT в поле access_token.

## Что проверить при реализации

- Вход реального пользователя на iOS и Android, возврат из SDK и отказ пользователя.
- Отказ при просроченном/отозванном токене и валидном токене чужого client_id.
- Один аккаунт на разных платформах; отсутствие обязательного email и защита от дублей при одновременном первом входе.
- Недоступность Яндекса, отсутствие токенов в логах, ротация и отзыв собственных сессий.
